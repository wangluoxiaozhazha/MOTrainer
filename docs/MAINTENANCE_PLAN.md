# 渐进维护与结构偿债计划

## 定位

MOTrainer 当前结构能够支持个人使用、功能验证和小步发布，不需要暂停功能开发进行
一次性重写。已经出现的结构债主要集中在少数中央类中，适合在后续功能改动触及相应
区域时渐进拆分。

本计划的目标不是追求抽象层数或形式上的整洁，而是降低改动波及范围，让内存写入、
状态回读、失败回滚和退出恢复更容易独立检查。

## 基本原则

- 先提交并保留已经验收的稳定状态，再开始结构调整。
- 以新增功能或修复问题的真实改动边界作为重构入口。
- 每次只拆一个可独立验收的职责，不进行跨项目的大规模重写。
- 重构前后保持相同的版本限制、会话检查、写入回读和失败回滚行为。
- 类或文件变少不是目标；只有依赖和职责真正分离才算完成。
- 单纯使用 `partial class` 拆文件只能改善阅读，不视为结构偿债。

## 当前主要结构压力

### `MainForm`

当前同时承担界面构造、固定布局、会话轮询、功能状态同步、快捷键、自动编辑、设置
保存和退出恢复。继续增加界面功能时，容易让局部改动影响整个窗口生命周期。

触发以下改动时，应顺便抽出对应边界：

- 新增或明显调整单位操作：抽出单位操作面板及其状态同步。
- 新增超武交互：抽出超武选择面板和执行入口。
- 扩展补丁或 Hook 控件：抽出补丁状态呈现与切换协调器。
- 再次修改轮询策略：引入可比较的界面状态快照，只更新发生变化的属性。

`MainForm` 最终应主要负责创建组件、连接事件和管理窗口生命周期，而不是包含每项
功能的全部控制逻辑。

### `GameActionService`

当前统一处理单位、阵营、超武、普通补丁、特殊 Hook 和自动维修。保留它作为 WinForms
的稳定入口是有价值的，但后续新增功能不应继续把所有实现直接堆入这个类。

建议按真实需求逐步委托给：

- `UnitActionService`：选中单位等级、生命值和归属；
- `FactionActionService`：经济与投降；
- `SuperweaponService`：超武参数校验、载荷生成和执行；
- `PatchFeatureService`：普通补丁与特殊 Hook 的统一分派。

这些服务应共享同一套会话取得和版本校验入口，避免各自形成不同的安全判断。

### 测试结构

当前轻量烟雾测试已经提供重要保护，但测试入口和用例集中在单个大文件中，且测试项目
会直接链接部分 WinForms 源文件。

当下一批测试加入时：

- 按 Session、Selection、Actions、Patching、Hooks、Settings 等领域拆分测试文件；
- 保留当前无第三方测试框架的轻量运行方式，除非现有方式确实妨碍定位或自动化；
- 优先测试实际项目程序集，避免长期维护测试项目中的源文件副本；
- 继续覆盖未知状态拒绝、部分写入回滚、重新附加和退出恢复。

### Hook 公共逻辑

现有快速生产、选中单位事件和科技全开 Hook 都包含远程页分配、入口验证、写入、回读、
回滚和释放流程。它们存在重复，但当前不立即统一。

只有出现以下情况之一时再抽取公共事务层：

- 增加第四种远程 Hook；
- 同一种回滚或远程页问题需要在多个 Hook 中重复修复；
- 已有测试能够覆盖抽取前后的完整安装与恢复语义。

这部分宁可暂时重复，也不要用未经验证的通用抽象模糊不同 Hook 的安全差异。

## 性能与部署边界

结构拆分本身不会明显提高运行性能，也不应改变发布形态。程序仍保持单一 WinForms
入口、Core 程序集、简体中文卫星资源和 x86 `.NET Framework 4.8` 发布目标。

性能优化应针对可观测问题单独实施，例如：

- 减少不必要的进程探测和跨进程内存读取；
- 只在状态发生变化时更新 WinForms 控件；
- 避免整组控件反复禁用、启用或重绘；
- 防止自动编辑轮询发生重入。

不能为了结构拆分而放松这些运行边界。

## 每次渐进重构的验收

每次结构调整至少应满足：

1. 只覆盖本次功能实际触及的职责；
2. 不改变配置键、补丁 ID、快捷键 ID 和版本 Profile；
3. Release 构建无警告和错误；
4. 全部烟雾测试通过；
5. 对受影响功能进行一次实际界面或游戏内验收；
6. 若涉及写入或 Hook，确认关闭程序时仍能恢复本次拥有的状态。

## 暂不采用

- 一次性重写 WinForms 或 Core；
- 为个人工具引入大型依赖注入或 UI 架构框架；
- 仅为了减少行数而创建大量薄包装类；
- 在没有新增 Profile 需求前重做版本配置系统；
- 在回滚语义尚未被完整测试前统一全部 Hook 实现。
